## Принципы продукта (из ТЗ, не нарушать)

- Журнал важнее программы: любую тренировку можно внести без шаблона и задним числом. Шаблоны и очередь Т1 → Т2 → Т3 — надстройка.
- Ничего не теряется: каждое изменение сразу пишется в IndexedDB и в очередь синхронизации; без сети всё работает.
- Приложение не решает за человека: никаких автоматических весов, целей и оценок. Бейдж «+2,5 кг» и таймеры отдыха и AMRAP нарисованы на макетах, но в MVP не входят.
- Очередь сдвигается только при завершении тренировки из этой очереди; свободные тренировки и пробежки её не трогают.
- Всё, что читает записанную тренировку или считает статистику, — чистая функция в `client/src/domain/` с тестом рядом (`*.test.ts`).

## Архитектура (целевая)

- npm workspaces: `shared/` (Zod-схемы — единственный источник типов через `z.infer`), `client/` (React, Vite, vite-plugin-pwa, Zustand, Dexie), `server/` (Fastify, Drizzle), `design/` (`tokens.json` из артефакта → `tokens.css`), позже `site/` (Astro).
- Синхронизация:
  - на сервере одна таблица `records(user_id, collection, id, data jsonb, updated_at, deleted_at, seq)`;
  - pull — по серверному курсору `seq` (`GET /api/sync?since=`), а не по часам клиента; push — пачкой (`POST /api/sync`);
  - конфликт решает last-write-wins по `updatedAt` записи; удаление мягкое;
  - на клиенте `outbox` с ключом `collection:id`; `user_id` берётся только из сессии.
- Каталог упражнений RepDB статичен и лежит в бандле. Синхронизируются только свои упражнения, заметки и сопоставления. У seed-записей детерминированные id (`seed:*`), чтобы первый вход с двух устройств не плодил дубли.
- Следующий шаблон и комплекс вычисляются из истории завершённых тренировок, а не хранятся счётчиком.
- Клиент и API на одном origin: в dev `/api` проксирует Vite, в проде — Caddy. Сессия — httpOnly-cookie.

## Данные и форматы

- Хранение: вес — кг, дистанция — м, время — с, темп — с/км, скорость — км/ч; даты `YYYY-MM-DD` в часовом поясе пользователя. Форматирование только на экране: «85 кг × 8», «7:46 /км», «3,09 км», десятичная запятая.
- Темп с часов (`recordedPace`) показывается, расчётный хранится всегда. Подходы с противовесом (`load: assisted`) не входят в 1ПМ и показываются отдельно от подходов с отягощением (`added`).
- Импорт идёт по колонкам `import_template.csv`. Повторный импорт не создаёт дублей (ключ — дата + название тренировки); экспорт → импорт даёт те же данные.

## Ключевые технические решения (записать в DECISIONS.md)

- **Схемы.** Единственный источник — `shared/src/schemas/*`; в `client/src/domain/` только чистые функции. Это снимает противоречие промпта: там `schemas.ts` указан и в `client/domain`, и в `shared/`.
- **БД.** Drizzle с диалектом PostgreSQL. Локально и в тестах — PGlite (Postgres в WASM, без Docker: его на машине нет), в проде — `pg` по `DATABASE_URL`. Одни и те же миграции, переезд с SQLite не понадобится.
- **Хранение на сервере.** Одна таблица `records(user_id, collection, id, data jsonb, updated_at, deleted_at, seq)`, первичный ключ `(user_id, collection, id)`, `seq` берётся из серверной последовательности. Отдельные таблицы под сущности не нужны: статистику считает клиент. `data` проверяется Zod-схемой своей коллекции.
- **Синхронизация.** `GET /api/sync?since=<seq>` — курсор серверный, а не `updatedAt` клиента: так расхождение часов на устройствах не теряет изменения. `POST /api/sync` — пачка изменений. Конфликты решает last-write-wins по `updatedAt` на уровне записи, удаление мягкое (`deletedAt`). На клиенте `outbox` с ключом `collection:id`, поэтому повторные правки одной записи схлопываются в одну.
- **Офлайн на iPhone.** В PWA на iOS нет Background Sync. Синхронизация идёт при старте, по событию `online`, при возврате в приложение (`visibilitychange`), раз в 60 с, пока приложение на экране, и через 2 с после записи. Вход нужен один раз, дальше приложение открывается без сети. При ответе 401 очередь изменений сохраняется и уходит после повторного входа.
- **Коллекции.** `sessions`, `templates`, `queues`, `complexQueue`, `complexes`, `exercises` (свои), `exerciseNotes` (заметки к упражнениям каталога), `exerciseAliases` (запомненные при импорте сопоставления), `settings`. Каталог RepDB статичен, лежит в бандле и не синхронизируется.
- **Seed.** У seed-записей детерминированные id (`seed:template:t1` и т. п.). При первом входе с пустым сервером клиент создаёт Т1–Т3, очередь, #001–#024 и очередь комплексов. Если два устройства войдут одновременно, записи совпадут по id и дублей не будет.
- **Очередь вычисляется из истории.** Следующий шаблон = слот последней *завершённой* тренировки этой очереди + 1. Ручную позицию можно задать отметкой `positionSetAt`. Поэтому удаление тренировки и синхронизация не ломают очередь, а свободная тренировка и пробежка её не трогают по построению.
- **Дополнения к модели плана:**
  - `Session.startedAt` / `finishedAt` — для «Завершить» и сдвига очереди;
  - `cardio.name` — для обратного экспорта колонки `exercise`;
  - `inShort` у блока шаблона — для кнопки «Короткая»;
  - id упражнений: `repdb:*` — каталог, `splav:*` — встроенные свои, uuid — созданные пользователем.
- **Шрифты** подключаются локально через `@fontsource` (кириллица): так они работают офлайн и не зависят от Google.
- **Чего нет в MVP.** Таймеров отдыха и AMRAP, бейджа «+2,5 кг» с макета, переключателя единиц (только кг и км). На экране тренировки есть время с начала: это часы тренировки, а не таймер, из них заполняется длительность.

### Этап 0.5. Аккаунт и синхронизация
- `server/src/db`:
  - таблицы `users`, `login_codes`, `auth_sessions`, `records`, индекс `(user_id, seq)`;
  - выбор драйвера: PGlite (файл в `server/.data`) или pg;
  - миграции через drizzle-kit.
- `server/src/auth`:
  - эндпоинты: `POST /api/auth/code`, `POST /api/auth/verify`, `GET /api/auth/me`, `POST /api/auth/logout`;
  - код — 6 цифр, в базе хранится HMAC с `AUTH_SECRET`;
  - живёт 10 минут, одноразовый, не больше 5 попыток; rate limit по IP и почте;
  - токен сессии — 32 случайных байта, в базе хранится его хэш;
  - cookie `httpOnly; Secure; SameSite=Lax` на 90 дней, продлевается при использовании;
  - почта: в dev код печатается в консоль, в проде уходит через SMTP из env.
- `server/src/sync`: `GET` и `POST /api/sync`. Конверт записи проверяется Zod-схемой из `shared/src/sync.ts`. Проверку `data` по коллекциям подключит этап 1. `user_id` берётся только из сессии.
- `client/src/sync`:
  - `saveRecord()` в одной транзакции пишет запись и `outbox`;
  - движок: сначала push, затем pull, входящие изменения применяются по LWW;
  - курсор хранится в `meta`;
  - статус в Zustand: «синхронизировано», «не синхронизировано (N)», «нет сети», «ошибка»; значок в шапке.
- `features/auth`: экран «Вход» по `Login.dc.html`: почта → код, без кнопок Apple и Яндекс. Выход: если очередь изменений не пуста, предупредить, затем очистить Dexie.
- Тесты:
  - сервер через `fastify.inject` и PGlite в памяти: срок кода, попытки, одноразовость, изоляция пользователей (A не читает и не пишет B), LWW, постраничный курсор;
  - клиент через fake-indexeddb: запись без сети → push → второе «устройство» получает её через pull.
- **Готово, когда:** запись, внесённая на iPhone без сети, появляется в браузере на ПК под тем же аккаунтом после связи; чужие данные по API недоступны.

### Этап 2. Журнал
- `features/workout` по `Workout.dc.html` и `WorkoutComplex.dc.html`:
  - шапка: время с начала и «Завершить»; дата меняется, можно внести задним числом;
  - блоки: сила, суперсет (общая карточка с кругами), кардио, комплекс, мобильность; «Добавить блок»;
  - выбор упражнения — поиск по каталогу и своим;
  - у упражнения прошлый результат и заметка; строка подхода: №, прошлый, кг, повторы, RPE, отметка;
  - «+ Подход» копирует предыдущий; отягощение и противовес; на сторону; время для статики;
  - кардио: вид, роль, дистанция, время, темп (авто, или с часов), пульс, этажи, наклон, RPE;
  - комплекс: ссылка на #, формат, лимит, результат (раунды + повторы, время или сумма), RPE, прошлая попытка и рекорд;
  - итог: время, тоннаж, км, RPE тренировки, заметка.
- Каждое изменение сразу пишется в Dexie. Поля крупные (от 44 px), `inputmode="decimal"`.
- `domain/`: `lastPerformance.ts`, `sessionType.ts` (тип по блокам без разминок, финишей и мобильности), `summary.ts` (тоннаж, км, длительность) — с тестами.
- Сегодня: «Свободная тренировка» и последние тренировки. Временная история в Прогрессе: поиск, фильтр по типу, редактирование, удаление.
- **Готово, когда:**
  - любую тренировку из `workouts_history.md` и `import_template.csv` можно внести вручную;
  - «Тренировка 1» от 20.10.2026 вносится с телефона за 3 минуты;
  - закрытие приложения посреди тренировки ничего не теряет.

### Этап 3. Импорт и экспорт
- `domain/importCsv.ts`:
  - строки → `Session[]` и отчёт;
  - UTF-8 с BOM и без, разделитель `,` или `;`, десятичная точка или запятая; Excel — первый лист через SheetJS;
  - объединение строк по date + session, блоков по order, суперсетов по букве;
  - ошибки и предупреждения — по разделу 5 плана и промпту, включая расхождение темпа больше 5%.
- `domain/exportCsv.ts`: те же колонки. Отдельно — полный JSON всех коллекций.
- Профиль → Импорт:
  - экран проверки: сводка, ошибки и предупреждения с номерами строк;
  - сопоставление новых названий: выбрать существующее или создать своё; выбор запоминается в `exerciseAliases`;
  - совпадение date + название → замена с подтверждением, id сохраняется.
- Экспорт на iPhone — через `navigator.share` с файлом, если не поддерживается — обычное скачивание. Парсеры подгружаются динамически.
- Тесты:
  - каждая строка `import_template.csv` разбирается в ожидаемую структуру;
  - 7:46 показывается, 7:49 хранится;
  - +10 кг (added) и 18,5 кг (assisted) различаются;
  - `parse(export(parse(csv))) ≡ parse(csv)`;
  - повторный импорт без дублей;
  - варианты файла: `;`, BOM, xlsx.
- **Готово, когда:** шаблон импортируется без ошибок (предупреждения о порядке дат ожидаемы), повторный импорт не дублирует, экспорт → импорт даёт те же данные.

### Этап 4. Шаблоны и очередь
- `domain/queue.ts`: следующий шаблон и номер цикла, следующий комплекс. Очередь комплексов сдвигается, когда завершена тренировка с блоком комплекса, равным ожидаемому. Тесты на сценарии приёмки.
- План по `Plan.dc.html`:
  - очередь Т1 → Т2 → Т3 в стиле дорожек, ручная позиция, «Новый цикл»;
  - шаблоны и редактор: блоки, упражнения, план подходов, повторов и веса, отметка «в короткой версии»;
  - библиотека #001–#024 с отметками «рекорд», «следующий», «не делал» и редактированием.
- Сегодня по `Main.dc.html`:
  - тёмная карточка следующей тренировки: состав, прошлые веса, «Начать» и «Короткая»;
  - следующий комплекс, последняя пробежка.
- Тренировка из шаблона предзаполняет поля прошлым результатом. Это копия, а не рекомендация: записать в DECISIONS.
- **Готово, когда:** завершение Т1 делает следующей Т2; свободная тренировка и пробежка очередь не сдвигают.

### Этап 5. Прогресс
- `domain/metrics.ts`:
  - e1RM по Эпли (подходы до 12 повторов, противовес не входит);
  - рабочий вес, лучший подход, тоннаж по неделям, средний RPE;
  - кардио: группы «Бег» (run + treadmill), «Вело» (bike + indoor_bike), «Другое»; км и минуты по неделям; темп только у `role: main`; лучшие результаты;
  - история комплексов;
  - баланс по типам по неделям, теплокарта за год, недели подряд.
- Правило минут силы (длительность тренировки минус известные минуты остальных блоков) — в DECISIONS.
- UI по `Progress.dc.html`: вкладки Сила, Кардио, Комплексы, Баланс. Графики на Recharts, теплокарта — своё SVG. Ниже — история с поиском, фильтром, редактированием и удалением (переносится из этапа 2).
- **Готово, когда:** цифры совпадают с ручным расчётом на контрольных примерах и выполнены все 9 критериев приёмки MVP из промпта.

### Этап 6. Деплой на российский сервер
- VPS (Timeweb Cloud или Selectel), Ubuntu LTS, Node 24, PostgreSQL, Caddy (HTTPS, статика клиента, прокси `/api`), systemd.
- Секреты в env. Миграции при деплое. Ночной `pg_dump` с копией вне сервера.
- SMTP: Яндекс 360 или Unisender Go, с SPF и DKIM. Домен `app.<домен>`.
- 152-ФЗ: политика обработки персональных данных и согласие на экране входа; уведомление в Роскомнадзор — до открытия приложения другим людям.
- **Готово, когда:** PWA ставится с боевого домена, код приходит на настоящую почту, данные синхронизируются между iPhone и ПК.
